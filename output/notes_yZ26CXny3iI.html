Introducing IndexedDB: Core Architectural Foundations, Key Database Concepts, and Choosing It Over Web Storage

IndexedDB is a client‑side, transactional NoSQL database that lives inside the browser’s sandbox. At its theoretical core it embodies the relational‑database concepts of sets and functions: an object store is a mathematically defined set  S = { o₁, o₂,… } where each element o is a JSON‑compatible value, and an index is a mapping I: S → K that extracts a key k from each object according to a deterministic projection function (e.g., o => o.email). This mapping enables the database engine to construct a balanced search structure—typically a B‑tree or B⁺‑tree—whose height h is O(log₍b₎ |S|) (with branching factor b). The objective of the engine is to minimize the expected I/O cost C = ∑ pᵢ·hᵢ, where pᵢ is the probability of accessing key kᵢ. By guaranteeing logarithmic lookup, insertion, and deletion costs, IndexedDB provides asymptotically optimal performance for large client‑side datasets while preserving the ACID guarantees of Atomicity, Consistency, Isolation, and Durability within a single‑origin transaction scope.

From a practical standpoint, the lifecycle of data in IndexedDB can be expressed in a step‑wise functional pipeline that mirrors Python’s context‑manager pattern. In pseudo‑Python, the flow is:

Each call to put, get, or open_cursor serializes the JavaScript object into the browser’s internal storage format, updates the B‑tree index, and writes a journal entry to guarantee durability. The transaction object ensures that either all modifications succeed or none are persisted, mirroring Python’s with‑statement atomicity guarantees.

When moving from prototype to production, several engineering considerations become decisive. Data leakage must be mitigated by never storing sensitive secrets (tokens, passwords) in clear text; instead, encrypt payloads client‑side using Web Crypto before persisting. Quota management varies by browser (typically 50 MB per origin, with user‑prompted extensions), so applications should implement graceful degradation—e.g., fallback to server sync or progressive data pruning—when onerror events signal quota exhaustion. Concurrency is limited to one active transaction per object store; developers must design non‑blocking UI flows that queue writes or employ versioned stores to avoid “blocked” states. Offline‑first architectures rely on IndexedDB as the source of truth; therefore, conflict resolution strategies (last‑write‑wins, CRDTs, or operational transforms) must be codified for eventual synchronization with a remote backend. Finally, scalability is bounded not by the engine but by the device’s storage and memory; bulk imports should be chunked into multiple transactions to keep the event loop responsive, and indexes should be kept minimal to avoid excessive B‑tree maintenance overhead.

**

** Think of IndexedDB as a high‑rise filing cabinet inside a secure office building. Each **object store** is a drawer labeled with a category (e.g., “Invoices”). Inside the drawer, every file (the JSON object) has a unique identifier stamped on its cover (the primary key). To find a file quickly, the cabinet has built‑in **index tabs**—like a card catalog—where each tab points to the exact drawer slot containing the matching file (e.g., “by client email”). When you need to add or remove files, you lock the drawer (start a transaction), perform all your changes, and then lock it back (commit), guaranteeing that no half‑finished rearrangement ever leaves the cabinet in an inconsistent state. If the building runs out of space (browser quota), the fire alarm (quota‑exceeded error) forces you to either archive older files to an off‑site storage (server sync) or discard non‑essential paperwork, ensuring the cabinet never overflows and remains fast to search. This mental model captures the organized, indexed, and transactional nature of IndexedDB while highlighting its role as a robust, offline‑ready storage solution.

#!/usr/bin/env python3
"""
Chapter 1 – Core Architectural Foundations & Paradigm Overview
Introducing IndexedDB (conceptually) – a client‑side, NoSQL‑style storage
engine.  While IndexedDB lives in the browser (JavaScript), the same
principles – databases, object stores, indexes, transactions, schemas –
can be demonstrated in pure Python using SQLite.  This script provides a
self‑contained, production‑grade example that mirrors the IndexedDB
workflow:

* Create a database (the “indexeddb” analogue)
* Define an object store (a table) with a primary key and secondary indexes
* Perform CRUD operations inside explicit transactions
* Query efficiently using the defined indexes
* Show why this approach scales far beyond the tiny limits of Web Storage
  (localStorage / sessionStorage).

The code is heavily annotated and split into logical steps so it can be
used as a teaching reference or a starter template for real projects.
"""

# --------------------------------------------------------------------------- #
# Step 0: Imports & Global Configuration
# --------------------------------------------------------------------------- #
import logging
import sqlite3
from contextlib import contextmanager
from pathlib import Path
from typing import Any, Dict, Iterable, List, NamedTuple, Optional, Tuple

# Configure a simple console logger – in production you would route this to
# files, syslog, etc.
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s – %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)
log = logging.getLogger(__name__)

# --------------------------------------------------------------------------- #
# Step 1: Database Path & Connection Helper
# --------------------------------------------------------------------------- #
DB_PATH = Path(__file__).with_name("indexeddb_demo.sqlite3")

@contextmanager
def get_connection() -> sqlite3.Connection:
    """
    Context manager that yields a SQLite connection with `detect_types`
    enabled for better Python ↔ SQLite type conversion.
    """
    conn = sqlite3.connect(
        DB_PATH,
        detect_types=sqlite3.PARSE_DECLTYPES | sqlite3.PARSE_COLNAMES,
        isolation_level=None,  # Autocommit disabled – we manage transactions.
    )
    try:
        # Enforce foreign‑key constraints (good practice for any relational DB)
        conn.execute("PRAGMA foreign_keys = ON;")
        yield conn
    finally:
        conn.close()

# --------------------------------------------------------------------------- #
# Step 2: Schema Definition (mirrors IndexedDB object store + indexes)
# --------------------------------------------------------------------------- #
class TodoItem(NamedTuple):
    """
    Represents a single to‑do entry.
    - `id` is the primary key (auto‑incremented, analogous to IndexedDB's keyPath).
    - `title` is the user‑provided description.
    - `completed` is a boolean flag.
    - `created_at` is a timestamp used for sorting / range queries.
    """
    id: Optional[int]  # None before insertion
    title: str
    completed: bool
    created_at: str  # ISO‑8601 string; SQLite stores TEXT for dates by default

def init_schema() -> None:
    """
    Creates the database schema if it does not already exist.
    Includes:
    * `todos` table – the object store.
    * Index on `completed` – enables fast look‑ups for “all unfinished”.
    * Index on `created_at` – enables chronological queries.
    """
    with get_connection() as conn:
        cur = conn.cursor()
        # Table creation – id is AUTOINCREMENT (like an auto‑generated key)
        cur.execute(
            """
            CREATE TABLE IF NOT EXISTS todos (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                title TEXT NOT NULL,
                completed INTEGER NOT NULL CHECK (completed IN (0,1)),
                created_at TEXT NOT NULL
            );
            """
        )
        # Secondary indexes (think of them as IndexedDB indexes)
        cur.execute(
            "CREATE INDEX IF NOT EXISTS idx_todos_completed ON todos (completed);"
        )
        cur.execute(
            "CREATE INDEX IF NOT EXISTS idx_todos_created ON todos (created_at DESC);"
        )
        conn.commit()
        log.info("Database schema ensured.")

# --------------------------------------------------------------------------- #
# Step 3: Transaction Management Helpers
# --------------------------------------------------------------------------- #
@contextmanager
def transaction(conn: sqlite3.Connection) -> Iterable[sqlite3.Cursor]:
    """
    Wraps a series of statements in a transaction.
    Usage:
        with get_connection() as conn, transaction(conn) as cur:
            cur.execute(...)
            cur.execute(...)
    If an exception bubbles out, the transaction is rolled back automatically.
    """
    cur = conn.cursor()
    try:
        cur.execute("BEGIN;")
        yield cur
        conn.commit()
        log.debug("Transaction committed.")
    except Exception as exc:
        conn.rollback()
        log.error("Transaction rolled back due to error: %s", exc)
        raise

# --------------------------------------------------------------------------- #
# Step 4: CRUD Operations (mirroring IndexedDB API)
# --------------------------------------------------------------------------- #
def add_todo(item: TodoItem) -> int:
    """
    Inserts a new TodoItem and returns the generated primary key.
    """
    with get_connection() as conn, transaction(conn) as cur:
        cur.execute(
            """
            INSERT INTO todos (title, completed, created_at)
            VALUES (?, ?, ?);
            """,
            (item.title, int(item.completed), item.created_at),
        )
        new_id = cur.lastrowid
        log.info("Added TodoItem id=%s title=%r", new_id, item.title)
        return new_id

def get_todo(todo_id: int) -> Optional[TodoItem]:
    """
    Retrieves a single TodoItem by primary key.
    Returns None if not found.
    """
    with get_connection() as conn:
        cur = conn.execute(
            """
            SELECT id, title, completed, created_at
            FROM todos
            WHERE id = ?;
            """,
            (todo_id,),
        )
        row = cur.fetchone()
        if row:
            todo = TodoItem(
                id=row[0],
                title=row[1],
                completed=bool(row[2]),
                created_at=row[3],
            )
            log.debug("Fetched TodoItem: %s", todo)
            return todo
        log.debug("TodoItem id=%s not found.", todo_id)
        return None

def update_todo(todo_id: int, **updates: Any) -> bool:
    """
    Updates fields of a TodoItem.
    Accepts any subset of columns as keyword arguments.
    Returns True if a row was modified.
    """
    if not updates:
        log.warning("No updates supplied for TodoItem id=%s.", todo_id)
        return False

    # Build SET clause dynamically while protecting against SQL injection.
    set_clause = ", ".join(f"{col}=?" for col in updates.keys())
    values = list(updates.values())
    values.append(todo_id)  # WHERE parameter

    with get_connection() as conn, transaction(conn) as cur:
        cur.execute(
            f"UPDATE todos SET {set_clause} WHERE id = ?;",
            values,
        )
        modified = cur.rowcount > 0
        if modified:
            log.info("Updated TodoItem id=%s with %s", todo_id, updates)
        else:
            log.warning("No TodoItem updated for id=%s", todo_id)
        return modified

def delete_todo(todo_id: int) -> bool:
    """
    Deletes a TodoItem by primary key.
    Returns True if a row was removed.
    """
    with get_connection() as conn, transaction(conn) as cur:
        cur.execute("DELETE FROM todos WHERE id = ?;", (todo_id,))
        removed = cur.rowcount > 0
        if removed:
            log.info("Deleted TodoItem id=%s", todo_id)
        else:
            log.warning("TodoItem id=%s not found for deletion.", todo_id)
        return removed

def list_todos(
    completed: Optional[bool] = None,
    limit: int = 100,
    offset: int = 0,
) -> List[TodoItem]:
    """
    Retrieves a paginated list of TodoItems.
    - If `completed` is set, the secondary index on `completed` is used.
    - Results are ordered by `created_at` descending (most recent first).
    """
    query = """
        SELECT id, title, completed, created_at
        FROM todos
    """
    params: List[Any] = []
    if completed is not None:
        query += " WHERE completed = ?"
        params.append(int(completed))
    query += " ORDER BY created_at DESC LIMIT ? OFFSET ?;"
    params.extend([limit, offset])

    with get_connection() as conn:
        cur = conn.execute(query, tuple(params))
        rows = cur.fetchall()
        todos = [
            TodoItem(
                id=row[0],
                title=row[1],
                completed=bool(row[2]),
                created_at=row[3],
            )
            for row in rows
        ]
        log.debug("Listed %s TodoItems (completed=%s).", len(todos), completed)
        return todos

# --------------------------------------------------------------------------- #
# Step 5: Demonstration / Simple CLI (acts as the “app” using the DB)
# --------------------------------------------------------------------------- #
def _demo() -> None:
    """
    Runs a short interactive demo that mirrors the typical IndexedDB usage
    pattern shown in the lecture:
    1. Initialise schema.
    2. Add a few records.
    3. Query by index (completed flag).
    4. Update a record inside a transaction.
    5. Delete a record.
    """
    import datetime
    import json

    # 1️⃣ Initialise / reset the DB for a clean demo run.
    if DB_PATH.exists():
        DB_PATH.unlink()
        log.info("Removed existing demo database.")
    init_schema()

    # 2️⃣ Add sample todos.
    now = datetime.datetime.utcnow().isoformat()
    sample_items = [
        TodoItem(id=None, title="Buy groceries", completed=False, created_at=now),
        TodoItem(id=None, title="Read a book", completed=False, created_at=now),
        TodoItem(id=None, title="Write blog post", completed=True, created_at=now),
    ]
    ids = [add_todo(item) for item in sample_items]

    # 3️⃣ Query unfinished items – uses the `completed` index.
    unfinished = list_todos(completed=False)
    print("\n🟢 Unfinished Todos:")
    print(json.dumps([t._asdict() for t in unfinished], indent=2))

    # 4️⃣ Mark the first item as completed (transactional update).
    first_id = ids[0]
    update_todo(first_id, completed=True)

    # Verify the update.
    updated = get_todo(first_id)
    print("\n🔄 Updated first Todo:")
    print(json.dumps(updated._asdict() if updated else {}, indent=2))

    # 5️⃣ Delete the second item.
    delete_todo(ids[1])

    # Final state – list everything.
    all_todos = list_todos()
    print("\n📋 All Todos after modifications:")
    print(json.dumps([t._asdict() for t in all_todos], indent=2))

if __name__ == "__main__":
    # Running the module directly launches the demo.
    _demo()

Key Takeaways

  • Use IndexedDB when you need to store and query large amounts of data client‑side that persist across sessions and work offline.
  • It’s ideal for fast, indexed searches; for simple key/value storage, localStorage/sessionStorage may be sufficient.
  • Grasp core concepts—database, object stores, indexes, transactions, and schema—since they apply to any database you’ll use later.

Schema Definition, Data Types, and Indexing Strategies in IndexedDB: Balancing Search Efficiency with Write Overhead

  1. Theoretical & Mathematical Foundations
    In IndexedDB the schema is a formal specification of the object store (analogous to a table) and its indexes. The underlying hypothesis is that data can be represented as a set of key‑value pairs, where keys are deterministic and indexes are auxiliary data structures that map a key to one or more records. The objective function that guides index design is a weighted sum of two competing costs:

\[ C_{\text{total}} = \alpha \cdot L_{\text{query}} + \beta \cdot L_{\text{write}} \]

where \(L_{\text{query}}\) is the expected latency of a typical read operation, \(L_{\text{write}}\) is the latency of an insert/update, and \(\alpha,\beta\) encode business priorities (e.g., read‑heavy vs write‑heavy workloads). The assumptions that underpin this model are (i) the index is a balanced B‑tree or LSM‑tree that offers \(O(\log n)\) lookup, (ii) the data distribution is roughly uniform unless otherwise specified, and (iii) the cost of maintaining an index is proportional to the number of index entries updated per write. By formalizing the trade‑off in this way, engineers can reason about the marginal benefit of adding an index versus the marginal write overhead it incurs.

  1. Step‑by‑Step Practical Mechanics (Python Simulation)
    In practice, defining a schema in IndexedDB involves three steps: (a) opening a database with a version number, (b) creating an object store with a keyPath or auto‑increment flag, and (c) adding one or more indexes.   1. Real‑World Production Engineering Implications
    In a production environment, schema evolution is handled via version upgrades (onupgradeneeded callbacks). Data leakage prevention requires that sensitive fields be encrypted before insertion and that the database be accessed only over secure contexts (HTTPS). Edge cases such as duplicate keys, null values, or large binary blobs must be addressed explicitly: IndexedDB enforces unique keys unless unique: false is specified, and large values trigger fragmentation that can degrade performance. Concurrency is managed through transactions that provide ACID guarantees; however, write amplification can become significant when many indexes are updated per transaction. Scalability considerations include the size of the index (which grows with cardinality), the cost of garbage collection for deleted entries, and the impact of background compaction on read latency. Monitoring tools should track transactionCount, indexSize, and writeLatency to detect when the cost model shifts.

  2. Balancing Search Efficiency with Write Overhead

#!/usr/bin/env python
# -*- coding: utf-8 -*-

"""
Production‑grade example illustrating:
* Schema definition & data‑type declaration
* Index creation & maintenance
* Search efficiency vs. write overhead trade‑off
* Simple transaction support (all‑or‑nothing batch updates)

The example mimics the concepts discussed for IndexedDB but is
implemented in pure Python for clarity and testability.
"""

# ----------------------------------------------------------------------
# Step 1: Imports & basic type definitions
# ----------------------------------------------------------------------
from __future__ import annotations

import itertools
import threading
from collections import defaultdict
from dataclasses import dataclass, field, asdict
from typing import Any, Callable, Dict, Iterable, List, Set, Tuple, Union

# ----------------------------------------------------------------------
# Step 2: Schema & record representation
# ----------------------------------------------------------------------
@dataclass(frozen=True)
class FieldSpec:
    """
    Specification of a single field in a schema.

    Attributes
    ----------
    name: str
        Human‑readable field name.
    dtype: type
        Expected Python type (e.g. str, int). Used for runtime validation.
    """
    name: str
    dtype: type


class Schema:
    """
    Collection of FieldSpec objects that defines the shape of a record.

    Example
    -------
    >>> person_schema = Schema([
    ...     FieldSpec("name", str),
    ...     FieldSpec("shirt_color", str),
    ... ])
    """

    def __init__(self, fields: Iterable[FieldSpec]) -> None:
        self._fields: Dict[str, FieldSpec] = {}
        for f in fields:
            if f.name in self._fields:
                raise ValueError(f"Duplicate field name: {f.name}")
            self._fields[f.name] = f

    @property
    def field_names(self) -> Tuple[str, ...]:
        """Ordered tuple of field names."""
        return tuple(self._fields.keys())

    def validate(self, record: Dict[str, Any]) -> None:
        """
        Ensure that a record conforms to the schema.
        Raises ``TypeError`` or ``KeyError`` on mismatch.
        """
        for name, spec in self._fields.items():
            if name not in record:
                raise KeyError(f"Missing required field: {name}")
            if not isinstance(record[name], spec.dtype):
                raise TypeError(
                    f"Field '{name}' expects {spec.dtype.__name__}, "
                    f"got {type(record[name]).__name__}"
                )
        # Disallow extra fields – keep the data model strict.
        extra = set(record) - set(self._fields)
        if extra:
            raise KeyError(f"Unexpected fields: {extra}")

# ----------------------------------------------------------------------
# Step 3: Index implementation
# ----------------------------------------------------------------------
class Index:
    """
    Simple inverted index mapping a field value → set of record IDs.

    The index is updated automatically on insert/delete operations.
    """

    def __init__(self, field_name: str) -> None:
        self.field_name = field_name
        self._index: Dict[Any, Set[int]] = defaultdict(set)

    def add(self, record_id: int, value: Any) -> None:
        """Add a record ID to the bucket for *value*."""
        self._index[value].add(record_id)

    def remove(self, record_id: int, value: Any) -> None:
        """Remove a record ID from the bucket for *value*."""
        bucket = self._index.get(value)
        if bucket:
            bucket.discard(record_id)
            if not bucket:               # prune empty buckets
                del self._index[value]

    def query(self, value: Any) -> Set[int]:
        """Return the set of record IDs that have *value* for the indexed field."""
        return set(self._index.get(value, set()))

    def __repr__(self) -> str:
        return f""

# ----------------------------------------------------------------------
# Step 4: Core in‑memory database with transaction support
# ----------------------------------------------------------------------
class InMemoryDB:
    """
    Minimal in‑memory database that respects a schema, maintains indexes,
    and provides atomic transactions.

    Thread‑safety: a single ``threading.RLock`` protects all mutations.
    """

    _id_counter = itertools.count(start=1)   # global unique IDs

    def __init__(self, schema: Schema, indexes: Iterable[str] = ()) -> None:
        self.schema = schema
        self._records: Dict[int, Dict[str, Any]] = {}          # id → record
        self._indexes: Dict[str, Index] = {
            field: Index(field) for field in indexes
        }
        self._lock = threading.RLock()

    # ------------------------------------------------------------------
    # Low‑level helpers (not exposed to end‑users)
    # ------------------------------------------------------------------
    def _store(self, record: Dict[str, Any]) -> int:
        """Insert a validated record, update indexes, and return its ID."""
        rec_id = next(self._id_counter)
        self._records[rec_id] = record
        for field, idx in self._indexes.items():
            idx.add(rec_id, record[field])
        return rec_id

    def _delete(self, rec_id: int) -> None:
        """Remove a record and clean up its index entries."""
        record = self._records.pop(rec_id)
        for field, idx in self._indexes.items():
            idx.remove(rec_id, record[field])

    # ------------------------------------------------------------------
    # Public API
    # ------------------------------------------------------------------
    def insert(self, record: Dict[str, Any]) -> int:
        """
        Insert a single record.

        Returns
        -------
        int
            The generated primary key.
        """
        with self._lock:
            self.schema.validate(record)
            return self._store(record)

    def bulk_insert(self, records: Iterable[Dict[str, Any]]) -> List[int]:
        """
        Insert many records atomically. If any record fails validation,
        *no* record is persisted (transactional guarantee).
        """
        with self._lock:
            # Validate everything first – cheap because we only check types.
            validated = [dict(r) for r in records]   # shallow copy
            for rec in validated:
                self.schema.validate(rec)

            # All good → perform inserts.
            ids = [self._store(rec) for rec in validated]
            return ids

    def get(self, rec_id: int) -> Dict[str, Any]:
        """Retrieve a copy of a record by its primary key."""
        with self._lock:
            return dict(self._records[rec_id])   # defensive copy

    def query(self, **criteria: Any) -> List[Dict[str, Any]]:
        """
        Simple equality query using indexed fields when possible.

        Parameters
        ----------
        **criteria: field=value pairs

        Returns
        -------
        List[Dict[str, Any]]
            Matching records (order undefined).
        """
        with self._lock:
            if not criteria:
                return [dict(r) for r in self._records.values()]

            # Prefer indexed fields to narrow the candidate set.
            indexed_fields = [f for f in criteria if f in self._indexes]
            if indexed_fields:
                # Intersect the ID sets of all indexed criteria.
                candidate_ids = None
                for field in indexed_fields:
                    ids = self._indexes[field].query(criteria[field])
                    candidate_ids = ids if candidate_ids is None else candidate_ids & ids
                # If intersection is empty we can short‑circuit.
                if not candidate_ids:
                    return []
            else:
                # No index – fall back to scanning all records.
                candidate_ids = set(self._records.keys())

            # Apply remaining (non‑indexed) filters.
            results = []
            for rec_id in candidate_ids:
                rec = self._records[rec_id]
                if all(rec.get(k) == v for k, v in criteria.items()):
                    results.append(dict(rec))
            return results

    # ------------------------------------------------------------------
    # Transaction handling
    # ------------------------------------------------------------------
    def transaction(self) -> "Transaction":
        """Create a new Transaction object bound to this DB."""
        return Transaction(self)

    # ------------------------------------------------------------------
    # Debug helpers
    # ------------------------------------------------------------------
    def __repr__(self) -> str:
        return (
            f""
        )

# ----------------------------------------------------------------------
# Step 5: Transaction class (all‑or‑nothing batch updates)
# ----------------------------------------------------------------------
class Transaction:
    """
    Context manager that batches inserts/deletes. If an exception occurs
    inside the ``with`` block, all changes are rolled back.
    """

    def __init__(self, db: InMemoryDB) -> None:
        self._db = db
        self._log: List[Tuple[str, Any]] = []   # ("insert", rec_id) or ("delete", rec_id, record)

    def __enter__(self) -> "Transaction":
        # Acquire the DB lock for the whole transaction duration.
        self._db._lock.acquire()
        return self

    def __exit__(self, exc_type, exc, tb) -> bool:
        if exc_type is None:
            # Commit – nothing to do because operations already applied.
            self._log.clear()
        else:
            # Rollback – undo in reverse order.
            for entry in reversed(self._log):
                action = entry[0]
                if action == "insert":
                    rec_id = entry[1]
                    self._db._delete(rec_id)
                elif action == "delete":
                    rec_id, record = entry[1], entry[2]
                    self._db._records[rec_id] = record
                    for field, idx in self._db._indexes.items():
                        idx.add(rec_id, record[field])
            # Swallow the exception? No – propagate it.
        self._db._lock.release()
        # Returning False re‑raises any exception that occurred.
        return False

    # ------------------------------------------------------------------
    # Transactional operations
    # ------------------------------------------------------------------
    def insert(self, record: Dict[str, Any]) -> int:
        """
        Insert a record within the transaction. The operation is logged
        so it can be undone if the transaction fails.
        """
        self._db.schema.validate(record)
        rec_id = self._db._store(record)
        self._log.append(("insert", rec_id))
        return rec_id

    def delete(self, rec_id: int) -> None:
        """
        Delete a record within the transaction. The original record is
        saved to allow rollback.
        """
        record = self._db._records[rec_id]
        self._db._delete(rec_id)
        self._log.append(("delete", rec_id, record))

Key Takeaways

  • Explicitly define a schema with clear data types (e.g., `name: string`, `shirtColor: string`) to guarantee consistency and efficient storage.
  • Create indexes on fields that are queried frequently (e.g., `shirtColor`) to accelerate lookups, but remember each index consumes additional disk space.
  • Adding an index adds write overhead: every insert or update must also update the index, so limit indexes to the most critical search paths.
  • Use IndexedDB transactions to batch data and index updates, ensuring atomicity and reducing the per‑operation cost of maintaining indexes.
  • Balance read vs. write performance: more indexes = faster reads but slower writes; choose indexes based on your application’s dominant access pattern.

Key Takeaways

  • Use the `onupgradeneeded` event to build the database schema only once (or when the version changes), ensuring the setup runs only during the initial open or upgrade.
  • Inside `onupgradeneeded`, create object stores with `db.createObjectStore(name, { keyPath: 'id' })`; the `keyPath` serves as the primary key for each record.
  • Define indexes on fields you’ll query frequently (e.g., `store.createIndex('color', 'color', { unique: false })`) to enable fast lookups without scanning the entire store.

  • Remember that object stores and indexes are immutable after creation—changing them requires incrementing the database version and handling the upgrade logic again.

def preprocess_and_split(df: pd.DataFrame, cfg: Config) -> Tuple[Pipeline, pd.DataFrame, pd.Series, pd.DataFrame, pd.Series]:
    """
    Build a preprocessing pipeline and split the data.
    Returns:
        - preprocessing pipeline (fit on training data)
        - X_train, y_train, X_test, y_test (as pandas objects)
    """
    # Separate features & target
    X = df.drop(columns=["target"])
    y = df["target"]

    # Identify column types
    numeric_cols = X.select_dtypes(include=["int64", "float64"]).columns.tolist()
    categorical_cols = X.select_dtypes(include=["object", "category"]).columns.tolist()

    logger.info(f"Numeric columns: {numeric_cols}")
    logger.info(f"Categorical columns: {categorical_cols}")

    # Define column‑wise transformers
    numeric_transformer = Pipeline(
        steps=[
            ("scaler", StandardScaler()),  # Standardise numeric features
        ]
    )
    categorical_transformer = Pipeline(
        steps=[
            # One‑hot encode, ignore unknown categories at inference time
            ("onehot", OneHotEncoder(handle_unknown="ignore", sparse_output=False))
        ]
    )

    preprocessor = ColumnTransformer(
        transformers=[
            ("num", numeric_transformer, numeric_cols),
            ("cat", categorical_transformer, categorical_cols),
        ]
    )

    # Train‑test split with stratification for class balance
    X_train, X_test, y_train, y_test = train_test_split(
        X,
        y,
        test_size=cfg.test_size,
        random_state=cfg.random_state,
        stratify=y,
    )
    logger.info(
        f"Data split – train: {X_train.shape[0]}, test: {X_test.shape[0]}"
    )

    # Fit preprocessor on training data only
    preprocessor.fit(X_train)
    logger.info("Preprocessor fitted on training data")

    return preprocessor, X_train, y_train, X_test, y_test

    fitted_models: Dict[str, Pipeline] = {}
    for name, pipeline in models.items():
        logger.info(f"Training {name} (grid‑search with limited params)")
        param_grid = cfg.param_grid.get(name, {})

        search = GridSearchCV(

            f"{name} best params: {search.best_params_} | best CV score: {search.best_score_:.4f}"
        )
        fitted_models[name] = search.best_estimator_

def evaluate_model(
    model: Pipeline,
    X_test: pd.DataFrame,
    y_test: pd.Series,
) -> Dict[str, float]:
    """
    Compute a suite of classification metrics on the test set.
    Returns a dictionary of metric name → value.
    """
    y_pred = model.predict(X_test)
    y_proba = (
        model.predict_proba(X_test)[:, 1] if hasattr(model, "predict_proba") else None
    )

    metrics = {
        "accuracy": accuracy_score(y_test, y_pred),
        "balanced_accuracy": balanced_accuracy_score(y_test, y_pred),
        "precision": precision_score(y_test, y_pred, zero_division=0),
        "recall": recall_score(y_test, y_pred, zero_division=0),
        "f1": f1_score(y_test, y_pred, zero_division=0),
    }

    if y_proba is not None:
        metrics["roc_auc"] = roc_auc_score(y_test, y_proba)

    return metrics
